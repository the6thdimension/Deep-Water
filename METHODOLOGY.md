# McMahon Simulation Methodology

A working framework — distilled from building **Deep Water** — for developing high-fidelity, performant, military 3D simulations in Unity.

This document is **alive**. Principles are added as they're discovered or hardened during real work, and cross-referenced to the code or scene where they were exercised. Vague aspirations get rewritten or removed. The goal is a concrete, falsifiable bible — not a manifesto.

---

## How to use this document

- **When you discover a principle while working, append it.** Don't wait for a dedicated session.
- **Prefer concrete and falsifiable** ("Tuning values live in ScriptableObjects, never as `const` or `[SerializeField]` literals on MonoBehaviours") over vague ("write clean code").
- **Ground every principle in a real case.** Reference the file, scene, system, or commit where the principle was exercised or where its absence caused pain. Abstract principles without provenance get demoted to "Candidates" until a real case anchors them.
- **Diagnose before prescribing.** When a principle came from a legacy code rewrite, state what the legacy pattern got wrong — the diagnosis is as valuable as the fix.
- **Promote and demote.** Principles graduate from `Candidates` → `Principles` → `Laws` as they prove themselves. Demote anything that turns out to be situational rather than universal.

---

## The Five Prime Virtues

These are the fixed points around which the methodology orbits. Every principle below should serve at least one of these; if it doesn't, it doesn't belong.

1. **Maintainability** — Code is read far more than written. Every change leaves the codebase easier to modify.
2. **Extensibility** — New vehicles, weapons, sensors, effects slot in by *adding* code, not rewriting it.
3. **Reliability** — Predictable across runs, frame rates, hardware, and load. Determinism where it matters.
4. **Testability** — Simulation logic must be reachable by automated tests. Untestable code is a design defect.
5. **Performance** — Real-time, high-fidelity sim is the target. Profile, then optimize. Don't be carelessly wasteful by default.

## Principles (working set)

*Concrete rules grounded in real cases. Subject to revision but currently load-bearing.*

### Configuration & data

- **P1. Tuning values live in ScriptableObjects, not in code.** Weapon profiles, sensor specs, vehicle stats, AI parameters, environmental constants — all SO-driven. No magic numbers, no `[SerializeField]` literals scattered on MonoBehaviours.
  - *Why:* Decouples tuning from compile. Lets designers and you iterate without rebuilding. Makes A/B and regression testing tractable.
  - *Origin:* Established as project-wide standard; mirrors the `Guided Fury/ScriptableObjects/` layout.

### Time & determinism

- **P2. Physics, ballistics, and sensor logic run on `FixedUpdate`.** Frame-rate independent. Two runs at different framerates must produce the same engagement outcome (given the same seeds).
  - *Why:* Sim integrity. A weapon system whose behavior depends on framerate is not a simulation, it's an animation.
  - *Origin:* Project-wide standard; will be tested via `RH Testing Suite` once a framerate-variance test exists.

### Module structure

- **P3. New systems follow the `Core / Modules / ScriptableObjects / Prefabs / Examples` layout.**
  - *Why:* Predictable navigation. The Core/Modules split forces a thinking pass on what's stable vs. what varies. Examples keeps the system self-demonstrating.
  - *Origin:* Mirrors `Assets/Guided Fury/`.

### Performance

- **P4. Burst / Jobs / ECS go on the hot paths only.** Many-entity physics, sensor sweeps, ballistic traces, swarm AI. Don't force DOTS on small systems — the complexity tax isn't worth it.
  - *Why:* Maintainability vs. performance balance. DOTS-everywhere is a different methodology with different costs.
  - *Origin:* Project-wide standard; not yet stress-tested against a real high-N system.

### Boundaries

- **P5. Vendor code is read-only by default.** Wrap, extend, or compose. Modify only with explicit permission.
  - *Why:* Upgradability and blast-radius control. A vendor patch that gets overwritten on the next package update is a silent regression.
  - *Origin:* Project rule; vendors include RealisticCarControllerV3, NWH, Obi, RootMotion, SensorToolkit, HurricaneVR, Cesium, FlightSimLite.

### Architecture

- **P6. Simulation core is plain C#; `MonoBehaviour` is a thin adapter.** Integration, guidance, control, and state-evolution code lives in pure C# classes/structs — no `MonoBehaviour`, no `Time.deltaTime`, no Unity lifecycle dependency. `MonoBehaviour` exists only to (a) pump the simulation each `FixedUpdate`, (b) surface state to Unity transforms / rigidbodies, and (c) receive Inspector configuration.
  - *Why:* Three benefits in one rule. (1) **Testability** — pure C# is unit-testable in isolation without spinning up a scene. (2) **LOD/integrator swapping** — if state and integration are tangled into MonoBehaviour lifecycle, you can't cleanly swap implementations. (3) **DOTS migration path** — a Burst-friendly struct-based core can later be hoisted into Jobs/ECS without rewriting the math.
  - *Origin:* Promoted from candidate C1 when Guided Fury's LOD-swappable architecture made the rule non-negotiable. Reference implementation: `Assets/Guided Fury/Core/Missile/MissileEntity.cs` (pure C#) + `MissileBehaviour.cs` (adapter).

- **P7. Determinism via fixed-seed RNG injected through SO config.** Anything in the sim core that needs randomness (seeker noise, INS drift, fuze jitter, dispersion patterns) takes its RNG as a constructor/field parameter, not from `UnityEngine.Random` or `System.Random` with default seed. Seeds come from the `MissileProfileSO` (or equivalent per-system SO).
  - *Why:* Reproducibility. Two runs with the same scenario and seed must produce the same outcome — required for replays, AAR, regression tests, and credible balancing. Hidden global RNG defeats all of these.
  - *Origin:* Promoted from candidate C2 when Guided Fury L4+ planning surfaced the need (gimbal noise, glint, seeker jitter). Will be exercised first by L5 HWIL.

## Patterns (recurring shapes worth naming)

*Reusable structural patterns observed across systems. Less mandatory than Principles — more like vocabulary.*

- **Pat1. SO-Profile + Pure-Core + MB-Adapter.** Three-layer shape for any simulation system:
  1. **`XxxProfileSO`** — authored asset holding tuning data for the system. May contain runtime-struct equivalents (`XxxProfileData`) that are unmanaged-friendly.
  2. **`XxxEntity`** — pure C# class/struct holding state + behavior. No Unity references. The simulation lives here.
  3. **`XxxBehaviour`** — `MonoBehaviour` adapter. Owns the entity. Pumps it each `FixedUpdate`. Surfaces state to the Unity scene.
  - *Where exercised:* Guided Fury (`MissileProfileSO` + `MissileEntity` + `MissileBehaviour`). To be replicated for sensors, vehicles, AI agents.

## Anti-patterns (things we've learned not to do)

*Catalogued from legacy code or mistakes. Each entry: what it looks like, why it fails, what to do instead.*

- **AP1. Reflection-based SO → component field setting.** Setting private fields by string name via `Type.GetField("fieldName", ...)`.
  - *Where seen:* Legacy `Assets/_Archive/Guided Fury_legacy/ScriptableObjects/MissileConfigSO.cs:237–251`.
  - *Why it fails:* Silent breakage on rename/refactor (no compile error). Bypasses encapsulation. Untestable in isolation (depends on private field layout). Makes the SO's contract invisible to any tool, including the IDE.
  - *Do instead:* Public `Apply(in ProfileData data)` methods on the target, or pass an unmanaged `ProfileData` struct directly into the entity constructor. Names verified at compile time.

- **AP2. Physics simulation in `Update()`.** Calling `Rigidbody.AddForce()`, integrating velocity, or stepping aero from `Update()` instead of `FixedUpdate()`.
  - *Where seen:* Legacy `Assets/_Archive/Guided Fury_legacy/Core/MissileBase.cs:79–112` (calls `missilePhysics.UpdatePhysics()` from `Update`) and `MissilePhysics.cs:85–142` (uses `Time.deltaTime` while applying rigidbody forces).
  - *Why it fails:* Non-deterministic across framerates. Fights the PhysX solver, which steps separately on `FixedUpdate`. Engagement outcomes change with display refresh rate. Untestable, unreplayable, unbalanceable.
  - *Do instead:* All simulation-step work happens in `FixedUpdate()` with `Time.fixedDeltaTime`. P2 is the rule; this anti-pattern is the diagnosis.

- **AP3. Module auto-discovery by component scan.** Discovering "modules" via `GetComponents<MonoBehaviour>()` and filtering by interface.
  - *Where seen:* Legacy `Assets/_Archive/Guided Fury_legacy/Core/MissileBase.cs:308–320`.
  - *Why it fails:* Magic — what's attached affects behavior implicitly. Hard to reason about from the code alone (you must inspect the prefab). Order of attachment becomes a hidden dependency. Hard to test (you need a fully-built GameObject). Easy to break by accidentally adding an unrelated MonoBehaviour that implements the interface.
  - *Do instead:* Explicit composition. The profile SO (or entity constructor) names exactly which modules are active. If runtime variability is needed, expose a typed registry, not a scan.

- **AP4. Cross-component reach-around via public side-channel.** Component A calls a public method on component B that exists solely to let A poke B's state.
  - *Where seen:* Legacy `MissileGuidance.cs:141–143` calls `missileBase.GetPhysics().OnGuidanceUpdate(targetPosition)`.
  - *Why it fails:* The "side-channel" method has no real owner — it's neither input (no interface contract) nor event (no subscription). It pretends to be encapsulation while leaking it. Refactor blast-radius is huge because the call is invisible to the type system.
  - *Do instead:* A clean interface: guidance produces a `Command` struct; the integrator consumes it. The contract is the struct, owned by neither side.

- **AP6. Runtime `AddComponent<Rigidbody>()` on game objects with arbitrary provenance.** Adding a `Rigidbody` (and trigger `Collider`) to a missile / projectile / similar at runtime to enable physics-trigger-based detection.
  - *Where seen:* First-draft `MissileBehaviour.EnsureFuzeTrigger` set up a kinematic Rigidbody + trigger SphereCollider in `Launch()`. Result: intermittent `AddComponent<Rigidbody>()` returning null on certain prefab paths → `NullReferenceException`, then cascading `Rigidbody.WritePose` / `Invalid AABB` errors as the half-initialized body tried to sync to a transform written by the integrator.
  - *Why it fails:* `[DisallowMultipleComponent]` on `Rigidbody` plus Unity's variable AddComponent behavior across prefab / runtime / Editor states produces null returns that defensive null-checks alone don't catch (because the failure mode includes "added but in a state where pose-sync explodes"). The whole approach yokes physics-engine internals to your detection logic.
  - *Do instead:* `Physics.OverlapSphereNonAlloc` from `FixedUpdate`. Simpler, no component lifecycle, deterministic, allocation-free with a static buffer, ignores triggers via `QueryTriggerInteraction.Ignore`. Reference impl: `Assets/Guided Fury/Core/Missile/MissileBehaviour.cs:CheckProximityFuze`.

- **AP5. Hardcoded `Shader.Find("Standard")` in pipeline-agnostic code.** Asset-creation code that always reaches for the legacy built-in `Standard` shader.
  - *Where seen:* First-draft `MissileRangeSceneBuilder` produced magenta materials in this URP project before being corrected.
  - *Why it fails:* `Shader.Find` returns null when the shader doesn't exist in the active render pipeline; Unity falls back to its magenta error shader. Worse, even after fixing the shader, `material.color` writes `_Color` only — URP/HDRP lit shaders use `_BaseColor`, so colors silently fail to apply. Every modern Unity project ships URP or HDRP; written this way, the bug surfaces immediately for everyone but the original author.
  - *Do instead:* Pick the shader from `GraphicsSettings.currentRenderPipeline.defaultMaterial.shader` with name-based fallbacks (URP/Lit → HDRP/Lit → Standard → Unlit/Color). Write color via `HasProperty("_BaseColor") ? SetColor(_BaseColor) : SetColor(_Color)` — preferably both, since `HasProperty` is harmless on the wrong shader. Reference helper: `Assets/Guided Fury/Examples/Scripts/RangeMaterials.cs`.

- **AP8. Adopting a vendor prefab as-is when your system owns motion.** Using a vendor / legacy prefab (`ESSM Shell.prefab`, an aircraft, a vehicle) as the instance for a system whose adapter writes the transform every FixedUpdate, without neutralizing the vendor's own physics / scripts.
  - *Where seen:* User assigned `Assets/rim-162essm/ESSM Shell.prefab` as `missilePrefab` on `GuidedFury_TestRunner`. Prefab ships with a non-kinematic `Rigidbody` (`m_UseGravity: 1`) and a legacy `ESSMHomingMissile6DoF` script. On launch the missile fell straight down — PhysX gravity (and the legacy script) overrode the new `MissileBehaviour`'s kinematic transform writes.
  - *Why it fails:* P5 says vendor code is read-only by default, but it doesn't say "instantiate it as-is." When your adapter owns motion (FixedUpdate transform writes, P2/P6), any other component on the same GameObject that ALSO writes the transform or applies physics forces is a hidden competitor. Worst case: silent fight, where one system wins on some frames and loses on others, producing erratic motion the user can't trace.
  - *Do instead:* In the adapter's Launch / activation path, **actively neutralize foreign motion drivers** on the same GameObject:
    - Any `Rigidbody`: force `isKinematic = true`, `useGravity = false`, zero velocities.
    - Any sibling `MonoBehaviour` outside your system's namespace: disable it on launch (or warn loudly).
    - The neutralization is opt-out via a serialized bool so a user who genuinely wants the vendor physics to coexist can disable it.
  - *Reference impl:* `Assets/Guided Fury/Core/Missile/MissileBehaviour.cs:NeutralizeForeignComponents`.

- **AP10. Scale-blind `TransformPoint` offsets around vendor prefabs.** Computing a follow/mount/spawn position as `foreign.TransformPoint(localOffset)` when the foreign object is a vendor prefab whose authored scale you don't control.
  - *Where seen:* `MissileCameraController` chase view. `chaseOffset (0, 4, -15)` was applied via `TransformPoint` on the spawned `ESSM Shell` prefab, whose root scale is `(65, 65, 100)`. The 15 m offset became ~1.5 km: the camera slingshotted 1300 m behind the launcher on fire and orbited the whole flight from a kilometer and a half away. Combined with AP8's embedded "Missile Cam" (far clip 1000) hijacking the display, the user-visible symptom was "camera doesn't track the missile; it disappears after a moment."
  - *Why it fails:* `TransformPoint` applies position, rotation, **and lossyScale**. On your own rigs scale is usually 1 and the bug never fires. Vendor art is routinely authored at arbitrary scale to fit some other engine or export pipeline, so any camera rig, hardpoint, muzzle, or effect anchor that offsets "in the vendor object's space" inherits that scale silently. The failure is proportional to the vendor's scale factor, so it looks like a physics or smoothing bug, not a transform bug — expensive to diagnose.
  - *Do instead:* For offsets around objects you don't author, compose position and rotation only: `pos = foreign.position + foreign.rotation * localOffset`. Reserve `TransformPoint` for hierarchies whose scale you own. Corollary of AP8: adopting a vendor prefab means neutralizing not just its motion drivers but also its *metric assumptions*.
  - *Reference impl:* `Assets/Guided Fury/Examples/Scripts/MissileCameraController.cs` (chase pose).

- **AP7. State-machine entry side-effects in per-step case bodies.** Setting state that should fire "on entry to stage X" inside the `case X:` body of a `switch` driven from per-step Step logic.
  - *Where seen:* First-draft `CatapultCycle.Step` set `cat.JbdRaised = true` inside the `case CatapultStage.Tensioned:` body. When the Spotted case detected timeout and called `Transition(Tensioned)`, the switch exited with `break` — the Tensioned case body did not run in that same step. Result: a one-step lag on every transition (`JbdRaised` was false for one frame after entering Tensioned, true for one frame after entering Retracting). The bug surfaced in `JBD_RaisedDuringTensionedThroughFiring_LoweredDuringRetracting` because the test asserted around the transition boundary.
  - *Why it fails:* "Entry" and "per-step ongoing" are different semantic operations. Conflating them in the same `case` body means every stage-entry side-effect is delayed by exactly one Step. For long-duration stages the lag is invisible; for short stages, near-boundary observers, or systems that gate on the flag (visuals, sounds, animator triggers) it manifests as a one-frame flicker every transition. Defensive workarounds (assert with margin in tests, add edge-detection guards in downstream consumers) treat the symptom, not the cause.
  - *Do instead:* Centralise transitions through a single `Transition(ref state, NextStage)` helper that:
    1. Sets the new stage and resets the stage timer.
    2. Calls an `OnEnter(ref state, NextStage)` hook where entry side-effects live.
   Per-step case bodies then only handle *ongoing* logic — timer-based stage completion, physics integration, motion. Reference impl: `Assets/Carrier Ops/Core/Catapult/CatapultCycle.cs:OnEnter`.

- **AP11. Asking the renderer for physical truth.** Buoyancy, ship motion or sensors querying state that a renderer advances on its own clock, e.g. HDRP Water's `ProjectPointOnWaterSurface` or search jobs.
  - *Where seen:* HDRP 17.4 Water (`HDRenderPipeline.WaterSystem.Simulation.cs`). `simulationTime` advances from `Time.time` once per *render* frame, inside the render pipeline. The CPU replica of the FFT and the GPU readback also update once per render frame. This project's HDRP asset uses `waterScriptInteractionsMode: GPUReadback`, which is asynchronous and arrives frames late.
  - *Why it fails:* A FixedUpdate query reads the sea at the last render frame's time, so at 30 fps and at 144 fps the same hull sees different water. That breaks P2 silently, because the numbers look plausible. It also can't run in an EditMode test, since there is no renderer.
  - *Do instead:* The sim core owns the physical field: Burst, on the fixed-step clock. The renderer *consumes* that field, here through an HDRP Water Decal that evaluates the same components. Verify the agreement by reading the renderer back once, in a test harness, never in the sim loop. Reference impl: `Assets/Sea State/Core/Sea/SeaSimulation.cs` + `Modules/Hdrp/HdrpSeaRenderer.cs`.

- **AP12. Loading assets before a Single-mode scene switch in an editor builder.** Loading ScriptableObjects or assets into locals, then calling `EditorSceneManager.NewScene(..., Single)` / `OpenScene`, then wiring them into the new scene.
  - *Where seen:* First-draft `SeaStateDemoSceneBuilder`. The switch unloaded assets nothing referenced, so `library` and `look` were dead objects when assigned. `objectReferenceValue` quietly stored null, and the scene saved with missing references. Play mode then reported it, but only because the director refuses a null library loudly.
  - *Why it fails:* Unity's fake-null objects pass the C# reference check while the native object is gone. The assignment does not throw.
  - *Do instead:* Load assets *after* the scene switch. Make the wiring helper refuse null and re-read the property to confirm it stuck. Reference impl: `Assets/Sea State/Examples/Editor/SeaStateDemoSceneBuilder.cs:SetField`.

- **AP13. Reading an instrument you haven't read the source of.** Attributing a measured error to the system under test when the measuring tool has its own blind spot.
  - *Where seen:* The Sea State render-vs-physics check. HDRP's `ProjectPointOnWaterSurface` reported a 0.19 m mean disagreement at Douglas 7, and I attributed it to HDRP's deformation blur in the v1 README. Reading the readback's source (`SimulationCPU.Deformation.cs`) showed it samples the decal as one vertical channel at the query point and ignores horizontal deformation. Compared like-for-like, the rendered field matched physics to 0.9 cm.
  - *Why it fails:* The fix chases the wrong cause. Here, blur compensation was built to close a 19 cm gap that the blur never caused; it closes 60 % of a real 2 cm gap instead. Worse, a wrong number gets published as a property of the system.
  - *Do instead:* Before trusting a comparison, state what each side actually measures, from source. Report the like-for-like number and the instrument's known omission side by side. Reference impl: `Assets/Sea State/Examples/Editor/SeaRenderAgreementCheck.cs`.
  - *Seen again (2026-10-23):* The same readback samples decal deformation with repeat addressing (`SignedMod` in `SimulationCPU.Utilities.cs`), while the GPU clamps. Far outside the decal square it tiled the near field across the horizon: the far field read 2.41 m Hs instead of 1.89 m at Douglas 4, and the first far-field calibration nearly absorbed the error. The zone tool now includes deformation only inside the square (`SeaFarFieldTools.Height`).

- **AP14. Verifying the field you computed instead of what the renderer draws.** Proving a rendering feature correct by measuring its own buffers (statistics, a CPU twin) without checking that the renderer consumes them.
  - *Where seen:* Sea State residual foam, 2026-10-23. The GPU foam field matched its CPU twin to 1e-5 and its streak statistics were right, yet on screen residual foam on and off looked the same. Forcing each decal output to 1 showed why: HDRP 17.4's water-decal graph template writes the foam pass as (R = surface, G = deep), while HDRP's foam pass reads (G, B). Every water-decal graph's surface foam is dropped, and its deep foam is drawn as surface foam. The near-field whitecaps had been on screen since v1 only through the deep-foam output.
  - *Why it fails:* Every check upstream of the hand-off passes, so confidence is high exactly where nothing reaches the pixels. The bug is in vendor glue nobody reads, so it survives indefinitely.
  - *Do instead:* For every output channel, run a forced-maximum smoke test once (set it to 1 and look). Keep a standing check at the last buffer the renderer reads; here, HDRP's own foam buffer correlated with the residual field (0.91–0.95 after the fix). Reference impl: `Assets/Sea State/Examples/Editor/SeaFoamTools.cs` (`AppendHdrpAgreement`) and the `hdrpFoamChannelWorkaround` seam in `HdrpSeaLookSO`.

- **AP15. Applying a distributed load at the probe's reference point.** A sampled load (buoyancy columns, drag panels, lift strips) applied at the sample's fixed reference point instead of where the load actually acts.
  - *Where seen:* Sea State `BuoyancyProbeJob` (2026-10-22 to 2026-10-23) applied each water column's buoyancy at the column centre. A vertical force's point only matters once the hull heels. Then it carries the whole "centre of buoyancy below centre of gravity" term of GM = KB + BM − KG. The 154 m box got GM = BM (5.29 m instead of 2.44 m) and rolled ~1.5× too fast. The Reckoning physics spike found it by putting both points side by side on one integrator: 6.35 s vs 9.46 s, ratio 1.49 measured against √(BM/GM) = 1.47.
  - *Why it fails:* Every upright check passes: draft, heave, the batched-equals-per-probe test. The defect lives only in a degree of freedom nobody tested. It is invisible by eye, because a fast roll still looks like a roll.
  - *Do instead:* Apply the load at its centroid: here the submerged part's, along the column axis (`BuoyancyModel.SubmergedCentroid`). Pin it with a static test against closed-form theory in the off-axis state, here the righting moment vs wall-sided GZ within 2 %, plus a dynamic period test.
  - *Seen again in the same fix:* the first version took the axis as the body's up unflipped. That puts the force above the wet part once a hull is upside down. The new tests all passed. The demo's uniform 2 m buoy, which correctly tipped over, then floated stable upside down. Test `InvertedBox_RightsLikeAnUprightBox` now pins the symmetry. Lesson: a test suite written for the defect you found does not cover the states your fix newly reaches. Run the real scene too.

- **AP16. Measuring a discretised model with itself.** Taking a body's reference numbers (displacement, KB, BM, centre of buoyancy) from the same coarse sampling the simulation runs on, then testing the simulation against them.
  - *Where seen:* General Quarters DDG-51 hull, 2026-10-23. The first authoring script measured the hydrostatics on the same 9 × 4 m grid of 300 columns that Sea State floats. Upright checks agreed with themselves to 0.01 %. Heeled 5°, the probes gave 7.6 % less righting moment than the GM the numbers claimed, and free roll ran 3.9 % slow. The cause: a column whose bottom sits just under the waterline counts in full in the waterplane's second moment, but it stops lifting after a few centimetres of heel. On 9 × 4 m columns that is a large share of the waterplane. A grid study (9 × 4 m up to 61 × 0.5 m) showed the error is aliasing, not monotonic: 17 × 2 m was as bad as 9 × 4 m.
  - *Why it fails:* Reference and simulation share the discretisation error, so every comparison between them reads zero. The error lives in an off-design state (heel), where no reference exists.
  - *Do instead:* Measure on a sampling shown to be converged (two resolutions agree; here 41 × 1 m and 61 × 0.5 m within 0.02 % on displacement and 0.2 % on BM). Simulate on a coarser grid chosen from the convergence table for its cost. Gate the coarse grid against the converged numbers in a test, in the off-design state. Reference impl: `ArtSource/General Quarters/author_ddg51_gq.py` (`HYDRO_*` vs `PROBES_*`) and `HullL0Tests.Heeled5Degrees_RightingMomentGivesTheLayoutGM`. At 25 × 1.5 m (2 183 columns), GM at 5° is 1.510 against 1.500 m, and PhysX free roll is 11.18 s against 11.14 s damped theory (11.04 s undamped, ζ 0.13 from the decay).

- **AP17. A damping term sized for one degree of freedom, applied to all of them.** A crude drag or damping law tuned for one motion (heave, roll) applied isotropically, so it also acts on motions it was never sized for.
  - *Where seen:* Sea State probe drag, found 2026-10-24 when General Quarters put engines on the DDG. Each probe's drag acted on the full relative velocity, using the probe's horizontal area. On the DDG hull at 30 kn that is 85 MN against 3.4 MN of thrust, so she could never pass about 9 kn. Nobody noticed, because the demo hulls never move.
  - *Why it fails:* Every test that exercises the motion it was sized for passes. The other degrees of freedom sit at zero in every scene until something finally drives them.
  - *Do instead:* Give a damping law per-axis scales in the body's frame and default them to the old behaviour. A body whose own model owns an axis switches the generic one off there. Pin it with a test in a rotated, heeled pose. Reference impl: `BuoyancyHullSO.dragAxisScale`, `BuoyancyModel.ProbeForce`, test `PerAxisDrag_ActsInTheHullFrame`.

- **AP18. Setting the net force at the centre of mass and forgetting the moment of what it stands for.** A body is driven by computing its acceleration elsewhere (here from MMG equations with added mass) and applying F = m·a at the centre of mass. The moments are then added only for the named forces (hull, rudders), not for the rest of the force they sum to (here the added-mass reaction).
  - *Where seen:* General Quarters `ShipDrive`, 2026-10-24. The roll moment took only the hull and rudder sway forces at their depths. Hard over at flank in PhysX, the ship lurched 7° inward, then swung 17.5° outward. With the full hydrodynamic sway force (m·a_y: the rudders' share at their depth, the rest at the hull's centre of pressure), it is 2.9° inward and 13.1° outward. The steady heel was right either way (7.4° vs 7.2°), so only a transient showed it.
  - *Why it fails:* A force applied at the centre of mass carries no moment. Whatever part of the real force distribution it silently stands for loses its moment, and the error lives only in transients.
  - *Do instead:* Write the moment balance from the total force, then split that total by where each part really acts. Check a step input in the engine, not only steady states. Reference impl: `Modules/Propulsion/ShipDrive.cs`.

- **AP19. A scenario kind that no test spawns.** A scenario type that can spawn several kinds of thing (sea-skimmers, aircraft, ships) where the tests only ever spawn one kind, so the other kinds' code paths have never run.
  - *Where seen:* General Quarters `ScriptedRaid`, written in slice 2 and found on the range in slice 5 (2026-10-24). Every headless raid test used sea-skimmers. The aircraft path removed an aircraft once it was farther than its launch range from the raid's origin, measured as slant range. An aircraft launches at that range and 6 km up, so its slant range starts beyond the limit, and every aircraft in the first standard raid was deleted on its first step.
  - *Why it fails:* A green suite says nothing about branches no test enters. Each value of a kind enum is a branch, and the one nobody spawned is the one that is wrong.
  - *Do instead:* Give every kind a scenario can spawn a test that spawns it and follows it through its whole life (appear, act, leave or die). Measure each distance in the plane the rule means: "flown out of the area" is ground range. Reference test: `RangeL0Tests.Raid_AircraftAtAltitude_FlyTheirPass_InsteadOfVanishingAtLaunch`.

- **AP20. Trusting an effect built for another render pipeline because the engine says its shader is supported.** Dropping a vendor particle prefab into an HDRP scene because `Shader.isSupported` is true and the asset store page shows it burning.
  - *Where seen:* General Quarters slice 6, 2026-10-24. `HD_Naval_Explosion` uses the built-in pipeline's "Particles/Standard Unlit". HDRP reports it as supported and draws it as untextured grey quads. The VFX Arsenal flames rendered, but at a size and brightness made for a close camera, not a ship at 2 km under HDRP exposure. The same explosion still sits in a Guided Fury ground detonation.
  - *Why it fails:* "Supported" means it compiles, not that HDRP gives it the passes, the exposure and the fog it expects. Effects are authored for a scale and an exposure as much as a pipeline.
  - *Do instead:* Probe every candidate effect in the target scene, at the target distance, under the scene's exposure, and look at a screenshot before adopting it. If it fails, build it on a shader written for the pipeline (a ForwardOnly pass, display-relative colour, the pipeline's fog). Reference impl: `Assets/General Quarters/Modules/Presentation/Shaders/GQ_Particle.shader`, `Editor/CombatEffectsBuilder.cs`.

## Candidates (under evaluation)

*Ideas that might become Principles. Not yet load-bearing. Promote when grounded in a real case.*

- **C3. Scene-as-test-fixture.** Use minimal Examples scenes as both demos and integration-test fixtures. Re-evaluate once `RH Testing Suite` integrates with scene loading.
- **C6. Unit tests are colocated with the system; integration/scenario tests are centralized in `RH Testing Suite`.** EditMode tests that bind tightly to integrator math, guidance laws, etc. live in `Assets/Xxx/Tests/Editor/` next to the implementation. Cross-system / scenario / replay tests go in `RH Testing Suite` so they're centrally discoverable. Promote when a second system adopts the pattern.
- **C7. Profile struct + SO-baked-once.** The SO authors data; `Bake()` produces an unmanaged struct that the entity carries for its lifetime. Live edits to the SO don't retroactively change in-flight instances. Promote when a second system (sensor, vehicle) adopts the pattern.
- **C4. `XxxState` struct as universal interchange.** For any system with multiple fidelity levels or integrators, a single unmanaged state struct serves as the lingua franca — every integrator reads from it, mutates it, writes back. Round-trip-safe across LODs even if some fields are unused at the lower tier. Promote when the L0→L4 ladder in Guided Fury has fully validated the round-trip.
- **C8. One physical field, two evaluators, one verified agreement.** When the GPU must *draw* what the CPU *simulates*, both evaluate the same function over the same data. That means one shared buffer layout (here `SeaFrameComponent`, 2 × float4), the same clock and the same phase convention. Prove the agreement with a readback correlation test rather than by eye. The GPU computes only what is seen; anything that changes a sim outcome stays on the deterministic CPU path.
  - *Exercised:* `SeaFieldMath.cs` ↔ `SeaWaves.hlsl`. Rendered vs physics like-for-like at Douglas 7 + swell: corr 0.99999, mean |Δ| 0.9 cm, max 3 cm (σ 2 m). Mirrored axes give corr ≈ 0, which proves the orientation. The packed SIMD kernel is a third evaluator, pinned to the reference by `PackedKernel_MatchesReference` (≤ 1 mm).
- **C11. An optimisation or fidelity fix ships with its A/B number, or not at all.** Measure every change against the same harness, on the same scenario, with the change on and off. Keep it only if the number moves and fidelity is pinned by a test.
  - *Exercised:* Sea State optimisation pass (`SeaBenchmark`, `SeaRenderAgreementCheck`). SIMD kernel ×5.5. Parallel foam calibration took the bake from 40 to 2.6 ms. Batched buoyancy went from ≈0.42 to 0.10 ms per step. Blur compensation took 2.2 cm to 0.9 cm, which was measured, so it was kept. `FloatMode.Deterministic` costs 16–21 %, which was measured, so it was kept for reliability. Batch-size tuning moved nothing, so it was not pursued.
- **C9. Named scales map to physics through cited tables kept as code; derived numbers carry their formula; authored numbers say so.** This extends Pat4. Each profile asset carries a `provenance` text naming the source of each value and flagging authored values ("AUTHORED: WMO gives only > 14 m"). The runtime UI shows each number next to its formula.
  - *Exercised:* `Assets/Sea State/Editor/DouglasProfileBuilder.cs`, `Examples/Scripts/SeaStateSelectorPanel.cs`.
- **C10. Query the world at the time the bodies' state belongs to.** At FixedUpdate n, rigidbodies hold their state from (n−1)·Δt. Environment clocks queried during FixedUpdate must read that time: advance them at the start of every step except the first, not at the end. Render the environment at the interpolated time, to match interpolated bodies (Pat5).
  - *Exercised:* `SeaStateDirector.FixedUpdate` / `RenderTimeS`.
- **C12. A conserved quantity is transported in conservative form; transport the grid can carry exactly moves the grid, not the data.** Uniform drift is carried by moving the grid (a sub-texel fraction plus whole-texel shifts, which are exact copies). The non-uniform part goes through a flux-form step, which conserves the quantity to rounding and cannot go negative below CFL 1.
  - *Exercised:* Sea State residual foam (`ResidualFoamGrid`, `ResidualFoamStepJob`, `SeaFoam.compute`). A semi-Lagrangian step with a compression factor created foam on convergence lines narrower than a texel: +34 % interior mass in 30 s, with or without a Catmull-Rom limiter. The flux form conserves it (test `Windrows_PileFoamOntoTheConvergenceLines_ConservingIt`). The drifting grid moves a patch 6 m with variance unchanged to 0.1 %, where bilinear resampling would add ~12 m². It also runs 5 taps instead of 16.
- **C13. When a renderer's parameters are not the physical quantity, calibrate against what it actually produces, measured, and solve the table at runtime.** Keep the table's method, spread and date with it. Average over the instrument's own fluctuation: a 250 m HDRP patch's Hs beats ±7 % instant to instant, and a table sampled over 0.15 s was non-monotonic.
  - *Exercised:* `FarFieldCalibration` + `SeaFarFieldTools.CalibrateFarField`. HDRP's far field went from 100–149 % to 98–101 % of the sea state's Hs at Douglas 2–8.
- **C14. Every element owns a fidelity ladder; a loadout picks each level, and an unbuilt level falls back out loud.** Each element sits behind one interface with one implementation per level, built by a factory from (level, profile) through one table of built levels. A request above the highest built level runs at that level and logs a fallback. Guided Fury's `MissileLod` was the precedent for one element; General Quarters makes it the contract for all of them, so the radar can be at L2 while the gun is at L0.
  - *Exercised:* `Assets/General Quarters/Core/Fidelity/FidelityLadder.cs`, the factories in `Cic/` and `Magazine/`, and `GuidedFuryBridge` (missile L4 without aero tables flies at L3 and says so). Tests: `Ladder_FallsBackToTheHighestBuiltLevel_AndSaysSo`.
- **C15. Resolve fast intercepts by closest approach over the step, not distance at the step's end.** At 1 300 m/s closing, a 20 ms step moves the gap 26 m, wider than a 10 m fuze, so an end-of-step check can step straight past a hit. Solve the minimum distance of the relative motion within the step.
  - *Exercised:* `Assets/General Quarters/Core/Magazine/Intercept.cs`. Test `Intercept_CatchesAPassBetweenTicks`: ends 13 m off, the pass at 2 m. The L0 raid's ESSM kills detonated 2.5–7.7 m from their targets.
- **C16. Calibrate one number per public figure, and name the figures you did not fit.** When public data cannot set every coefficient, choose the fewest free numbers, fit each to one figure, and keep the remaining figures as validation. Say in the asset and in each test which is which: CALIBRATED tests guard against regressions, VALIDATION tests are evidence. Record a residual you cannot close as a known gap; do not tune it away with an unphysical number.
  - *Exercised:* `Editor/Ddg51EngineRoomData.cs`, `Tests/Editor/EngineRoomL0Tests.cs`.
    - **Calibrated:** 4 numbers (appendage factor, γ_R, ℓ'_R, astern thrust) against 3 figures (top speed, turn diameters, stop time).
    - **Validated (7):** 18 kn rpm, stop distance, acceleration, zig-zag, IMO criteria, steady heel, plus the transient heel, which fails and is recorded as an L1 gap.
    - **Roll damping:** fitting it to Barry's peak heel would have needed ζ ≈ 0.5, so it was left AUTHORED at 0.1.
- **C18. Prove input bindings with virtual devices, one per device class.** "Works with a gamepad" is a claim about bindings nobody pressed. The Input System's `InputTestFixture` adds virtual devices and presses their controls, so each device class gets a test: keyboard and mouse, an XInput controller, and a generic HID pad. The generic pad is a `Joystick` layout with a hat and numbered buttons, the shape Unity gives a pad it does not recognise. Then drive the real build once with virtual devices queued in play mode, and check the orders that come out.
  - *Exercised:* `Tests/Editor/ConnTests.cs` (`ConnBindingTests`) for the 'Conn' map in the project-wide actions.
    - **What it caught:** Shift+A hard rudder only worked when Shift came first. A modifier composite that shares its key with another action in the same map fires only if the modifier is pressed first, even with `modifiersOrder` Unordered; a standalone action works in either order.
    - **And before that:** a Scale processor changes an axis's value but not its actuation, so two bindings on one action tie and the first key wins.
    - **Fix:** a plain Shift modifier action, combined in the reader.
- **C17. Calibrate in a fast mirror; ship in the engine; prove they agree.** Parameter sweeps through Unity cost a recompile and a domain reload each. A dependency-free mirror of the same equations runs hundreds of manoeuvres a minute. The engine code then re-derives what it can (fits, the appendage factor) from the same sources, and the tests must reproduce the mirror's numbers.
  - *Exercised:* `Calibration~/mmg_calibration.py` and `EngineRoomL0Tests` agree on every figure (199 rpm, TD 388 / 1,083 / 1,026 m, stop 60.4 s / 382 m, zig-zag 5.5° / 5.4°). The folder ends in `~`, so Unity ignores it.
- **C19. A seat is an issuer, not a code path.** The player and the AI give a ship the same Orders through the same door, so a seat can change hands mid-fight and the record does not change shape. Each AI decision is a named rule written to the engagement log with its numbers and its cause, then issued as an ordinary Order. Run the AI inside the fixed tick, before the core steps, and it stays inside the determinism contract.
  - *Exercised:* General Quarters slice 5. `Core/Captain/AiCaptain.cs` (rules C1-C4, T1), `Examples/Scripts/Range/TaoStation.cs` and `ConnController` all issue Orders through `ShipCombat.Issue`. With the AI as TAO, the headless saturation raid gives the same Fix on two runs (`Saturation_WithTheRealLoadout_ResolvesExplained_Repeats_AndStaysInBudget`), and a T1 confirmation cites the TEWA proposal it answers.
- **C20. The Fix pins a refactor of the core.** When a core keeps a per-tick fingerprint, an optimisation or tidy-up of it must leave a seeded run's final Fix bit-identical. That is C11's fidelity pin at no extra cost.
  - *Exercised:* slice 5 made TEWA build its sentence only when it logs one. It had been formatting it on every 10 Hz evaluation of every standing proposal, part of the core's 0.64 KB/frame of garbage on the range. The saturation run's Fix was `2AF5C040E4AC6B5E` before and after.
- **C21. A camera that draws part of the screen leaves the rest unpainted.** With a viewport rect, HDRP clears and draws only inside it. Pixels outside keep whatever an earlier frame left, so a dismissed dialog can still show through a gap between panels. The UI must paint every pixel outside the rect.
  - *Exercised:* the range's TAO seat (`taoCameraViewport`, the `.gq-backdrop` elements in `RangeScreen.uss`). The first build showed the closed debrief's text between the scope and the camera window.
- **C22. The core says where; presentation decides how.** A deterministic core writes what happened, where, with what and from where into its log, and none of that goes into its fingerprint. Presentation reads the log behind a cursor and never writes back. Prove it twice: the fingerprint is unchanged with the new data, and an on/off A/B of the whole presentation layer shows only its own cost.
  - *Exercised:* General Quarters slice 6. `EngagementEvent.Point / Weapon / Source`, `Modules/Presentation/CombatPresentation.cs`. The saturation Fix stayed `2AF5C040E4AC6B5E`; presentation on vs off costs about 0.2 ms of main thread, 0.03 ms of it in `GQ.Presentation`.
- **C23. A fast emitter's trail is a ribbon, not puffs.** Particles laid by distance read as a dotted line once the emitter outruns them (an ESSM at 700 m/s), and a dense enough stream costs thousands of particles per missile. A `TrailRenderer` ribbon that widens and fades over its life costs one mesh and reads as smoke at any range.
  - *Exercised:* `CombatEffectsBuilder.Trail`, checked from the missile camera in play mode.
- **C24. A regenerated asset keeps its GUID by being overwritten in place.** A builder that deletes and recreates a scene or asset gives it a new GUID each run, which breaks build settings and every reference to it, and shows as a churned `.meta` in every commit. Copy over the existing file and reimport it.
  - *Exercised:* `RangeSceneBuilder` (slice 6): `GQ_Range.unity` keeps GUID `281e3cf048c5db14188104849f24eb4e` across rebuilds.
- **C5. Replaced legacy code goes to `Assets/_Archive/`, never deleted outright until cutover is proven.** Original folder name + `_legacy` suffix; original `.meta` preserved so GUIDs survive. Lets you reference old behavior during rebuild and gives a clean rollback path. Promote after one full cutover proves the workflow.
